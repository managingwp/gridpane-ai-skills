# gridpane-gp-cli

Find and run the right `gp` command, safely. GridPane ships a large CLI that
wraps Nginx, PHP, MySQL, Redis, caching, WAFs and WP-CLI. When GridPane provides a
command, use it instead of editing generated files (see `gridpane-core`,
`references/paths.md`).

Load `gridpane-core` first. The full verified command list lives in
`references/command-reference.md`; read it when you need the exact flag.

## Prerequisites

- Root (or sudo) over SSH.
- `gridpane-core` loaded.
- Know the site URL and the web server (Nginx or OLS) where it matters.

## Workflow

1. **Identify scope.** Is this one site (`gp site {site.url} …`), all sites
   (`all-sites`), or the stack (`gp stack …`)? The blast radius follows from the
   area you pick.
2. **Find the command** in `references/command-reference.md`, or from help.
3. **Read the help output** before running anything mutating.
4. **Classify it.** [READ] runs freely; [WRITE] needs the confirmation block and a
   backup; [DESTRUCTIVE] needs the action named by the user.
5. **Run, then verify** with an observable check.

Discover commands:

```bash
# [READ] Area-level help, then drill in.
gp --help
gp site --help
gp stack --help
```

```bash
# [READ] Confirm GridPane's scripts are current before relying on help text.
gpupdate
```

## Commands

A small, high-value selection. See `references/command-reference.md` for the rest.

```bash
# [READ] Report state without changing it.
gp ngx -status
gp mysql -status
gp redis -status
```

```bash
# [WRITE] Clear every cache for one site. Reversible but has impact.
# Blast radius: site example.com only. Rollback: caches rebuild on next visit.
# Confirm before running.
gp fix cached example.com
```

```bash
# [WRITE] Switch a site's PHP version (reloads PHP for that site).
# Blast radius: site example.com only.
# Backup: note the current version first. Rollback: switch back.
# Confirm before running.
gp site example.com -switch-php 8.2
```

## Verify

After a change, confirm with an observable check: response headers for caching
(`X-Grid-Cache` for FastCGI or `X-Grid-SRCache-Fetch` for Redis page cache),
`gp php {version} -status` after a PHP switch, or the site serving 200 after a
routing change. "No error" is not verification.

## Rollback

Every [WRITE] command above includes its rollback. General rules:

- **Toggles/settings:** re-run with the previous value, or the `-off`/reset
  variant.
- **Service reload/restart:** no data change; the service returns on its own.
- **Managed config:** it is regenerated by `gp`; never hand-edit it, so there is
  nothing to restore beyond the setting itself.

## Gotchas

- **Server-wide commands hide in plain sight.** `gp site all-sites sync-*`
  affects **every site**. `gp fix cached` with **no** site URL clears caches for
  **every site** on the server. Treat both as server-wide [WRITE].
  - `gp fix cached example.com` → one site.
  - `gp fix cached` → all sites.
- **`gp stack …` edits the stack**, not a single site, and often reloads the
  service afterwards. Chaining several can reload repeatedly; use the documented
  `-no-reload` flag where available.
- **Restart vs reload.** Prefer `-reload`; `-restart` drops in-flight requests.
  Both are [WRITE].
- **`gp mysql get-pass root` prints a secret.** Never paste it into a transcript
  or commit it.
- **`gp wp` vs raw `wp`.** Use `gp wp {site.url} …` so WP-CLI runs as the correct
  site system user. `--ssh` is not supported through `gp wp`; use raw WP-CLI for
  that case (see `gridpane-wordpress`).
- **A zero exit from a backup command is not proof a backup exists.**
  `gpbup {site} -run-single-site local` only queues the job (task-spooler socket
  `/tmp/ts-socket-backups.<uid>`) and returns; with local backups off for that
  site the queued run backs up nothing and still exits 0. See
  `references/command-reference.md` before relying on either.
- **A local backup cron can exist while local backups are off.**
  `-set-backup-schedule` writes the cron when *any* backup type is enabled, so
  `Remote-Backups:ON` plus `Local-Backups:OFF` still leaves a daily local cron
  that no-ops on every run. Read `/var/www/{site}/logs/backups.env`, not the
  cron file.
- **A spinning backup button needs a manual backup, not a scheduled one.** Only
  `-local-single-site` / `-remote-single-site` post `/backups/backup`, the call
  that re-enables the panel. Run one in `tmux`; an SSH drop skips the callback.
