# gridpane-core

Orientation for GridPane-managed servers. Read this first so the rest of the
`gridpane-*` skills make sense: it defines the mental model, the paths, the `gp`
command conventions and the safety rules that the operative skills rely on.
This skill is read-only; it changes nothing.

For a worked request flow and how a GridPane box differs from a vanilla LEMP
server, read `references/stack-overview.md`.

## Prerequisites

- Root (or a sudo user) over SSH for server-side work. Some WP-CLI tasks run as
  the site's system user instead; see `gridpane-wordpress`.
- Know which web server the site uses: **Nginx** or **OpenLiteSpeed (OLS)**.
  Commands and paths differ. Confirm before acting.
- A GridPane API token in `GRIDPANE_API_TOKEN` only if you are using
  `gridpane-api`. Never commit or echo it.

Load the references on demand rather than all at once:

- `references/paths.md` — where files and logs live, and what `gp` regenerates.
- `references/gridenv.md` — `/root/gridenv` server state files: what they hold,
  which keys are secret, and how to read them safely.
- `references/site-env.md` — the per-site `logs/{site.url}.env`: recorded cache
  method (`cache-type`), PHP/pool, WAF and cron state, and secret keys.
- `references/ols.md` — the OpenLiteSpeed model: config tree, `gpols` commands,
  logs, LSCache, security and PHP (LSAPI).
- `references/gp-conventions.md` — how `gp` commands are shaped, read vs mutate.
- `references/safety.md` — the protocol and the exact confirmation template.
- `references/stack-overview.md` — request flow and server model.
- `references/sources.md` — every fact's source and the date checked.

For building or debugging your own tooling on a server (the `/usr/local/bin` +
`lib/` scripts, the `gp` dispatcher, where custom tools may live), see the
sibling `gridpane-tooling` skill.

## Workflow

1. **Identify the target.** Get the site URL, the web server in use (Nginx or
   OLS) and the blast radius (one site, the whole server, or the fleet).
2. **Classify every command before running it.** Every command in these skills
   carries **[READ]**, **[WRITE]** or **[DESTRUCTIVE]**. Run [READ] freely;
   propose [WRITE] and wait for confirmation; only run [DESTRUCTIVE] when the
   user names that exact action.
3. **Prefer `gp` over hand edits.** GridPane regenerates many files. A rule you
   hand-place in a managed file will be silently overwritten. Use the supported
   include locations in `references/paths.md`.
4. **Diagnose before you change.** Read logs and status first. Changing config
   before you know the cause hides the evidence.
5. **Back up and validate.** Copy any file to `<file>.bak-<timestamp>` before
   editing; run `nginx -t` (or the OLS equivalent) before any reload.
6. **Confirm the fix, then stop.** Verify with an observable check, not a
   feeling. Do not "tidy up" unrelated config afterwards.

## Commands

Check the server and stack (read-only):

```bash
# [READ] Confirm the web server in use.
gp ngx -status          # Nginx
gpols -status           # OpenLiteSpeed (verify exact flag against `gpols -h`)
```

```bash
# [READ] Show what gp subcommands exist before guessing syntax.
gp --help
gp site --help
gp stack --help
```

```bash
# [READ] Recent GridPane activity on this server (what changed, when).
tail -n 100 /var/log/gridpane.log
```

## Verify

GridPane-core itself makes no changes, so there is nothing to verify beyond
confirming you can read the server: `gp --help` responds, the site directory at
`/var/www/{site.url}` exists, and the expected web server service is running.

## Rollback

Not applicable: this skill only inspects. Any change is made by an operative
skill, which must carry its own backup and rollback.

## Gotchas

- **Managed files get overwritten.** `/etc/nginx/sites-available/{site.url}`,
  the PHP-FPM pool file and `.user.ini` are generated by `gp`/the control panel.
  Put customisations in the include paths in `references/paths.md`, never in the
  managed file itself.
- **`gp wp` vs raw WP-CLI.** `gp wp {site.url} ...` runs as the correct site
  system user. Running raw `wp` as root against site files is wrong and can
  reset ownership.
- **`gp site {site.url} ...` scope.** Most `gp site` commands touch one site.
  `all-sites` variants and `gp fix cached` (no site) affect **every** site on
  the server — treat those as server-wide [WRITE].
- **Ubuntu 22.04+ locks `/tmp` as noexec.** Some third-party apps need it
  unlocked; `gp server -tmp-noexec disable` does that but weakens a hardening
  control. See `references/paths.md`.
- **`/tmp` is cleared on reboot.** Do not store anything durable there.
- **`/root/gridenv` holds live credentials.** Read individual non-secret keys
  (`grep '^server-version:' ...`) rather than dumping the file; never edit it or
  print secrets. See `references/gridenv.md`.
