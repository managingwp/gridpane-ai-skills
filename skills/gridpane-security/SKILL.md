# gridpane-security

Security operations on GridPane: WAFs, Fail2ban, Cloudflare at the origin, and
first response to a suspected compromise. Read-only detection only for
compromise; this skill never writes or runs attack code.

Load `gridpane-core` first. Detail per area:

- `references/waf.md` — 6G/7G/ModSecurity: enable, read blocks, whitelist.
- `references/fail2ban.md` — jails, checking and unbanning IPs, Cloudflare bans.
- `references/cloudflare.md` — real IP, SSL mode, origin lockdown.
- `references/compromise-first-response.md` — contain, preserve, identify, clean, harden.

## Prerequisites

- Root (or sudo) over SSH.
- `gridpane-core` loaded.
- Know the site URL and whether the site is behind Cloudflare's proxy (orange
  cloud) or DNS-only (grey cloud).

## Workflow

1. **Read before you change.** WAF logs and Fail2ban status tell you what is
   blocked and by which rule.
2. **Whitelist, don't disable.** For a false positive, whitelist the specific
   rule rather than turning off a whole ruleset or firewall.
3. **Confirm any toggle.** WAF/Fail2ban changes are [WRITE]; a bad rule can cause
   an Nginx syntax failure that takes all sites offline.
4. **For a possible compromise:** contain and preserve evidence before cleaning.

Inspect current state:

```bash
# [READ] Fail2ban jails and current bans.
fail2ban-client status
fail2ban-client status wordpress-extra
```

```bash
# [READ] What is the 7G WAF blocking for a site?
tail -n 50 /var/www/example.com/logs/7g.log
```

```bash
# [READ] ModSecurity/7G events in the Nginx site error log.
grep -iE 'modsecurity|7g' /var/log/nginx/example.com.error.log | tail -n 30
```

```bash
# [READ] OLS: ModSecurity audit log and the site error log.
tail -n 30 /var/log/modsec_audit.log /var/www/example.com/modsec/modsec_audit.log 2>/dev/null
tail -n 30 /var/www/example.com/logs/example.com.error.log
```

## Commands

WAF toggles (per site, [WRITE]):

```bash
# [WRITE] Enable the 7G WAF for one site.
# Blast radius: site example.com only. Backup: the config is regenerated by gp.
# Rollback: `gp site example.com -7g-off`. Confirm before running.
gp site example.com -7g-on
```

```bash
# [WRITE] Whitelist a false positive by disabling ONE rule, via a 7G context
# include (see references/waf.md). Always `nginx -t` before reloading.
```

Fail2ban unban ([WRITE]):

```bash
# [WRITE] Unban an IP from the wordpress-extra jail.
# Blast radius: affects that jail's bans only. Rollback: it may re-ban if the
# behaviour continues. Confirm before running.
fail2ban-client set wordpress-extra unbanip 203.0.113.10
```

## Verify

- WAF: the blocked request from the log now succeeds, and Nginx reports no syntax
  error after `nginx -t`.
- Fail2ban: `fail2ban-client status {jail}` no longer lists the IP.
- Real IP: access logs show the visitor IP, not a Cloudflare IP.

## Rollback

- WAF toggle → the opposite `-off`/`-on`.
- WAF whitelist file → delete the include, `nginx -t`, `gp ngx -reload`.
- Fail2ban unban → the IP is re-banned if it misbehaves again; to make it
  permanent, add an Nginx deny or a firewall rule instead.

## Gotchas

- **A broken WAF rule takes the whole server down.** Custom 7G rules and
  whitelists live in Nginx includes; a syntax error means Nginx cannot reload at
  all. Always `nginx -t`.
- **Never copy 6G rules into 7G configs.** They are not compatible and will cause
  an Nginx syntax failure.
- **OLS has no 6G.** Use 7G and ModSec; their paths and the per-site
  `ols/7g-*.conf` allow/deny files differ. Regenerate with `gpols site` /
  `gpols httpd`, not `gp ngx -reload` (see `references/waf.md`).
- **Behind Cloudflare, banning the visitor IP at the origin does nothing useful**
  — the traffic still arrives from Cloudflare. Ban at Cloudflare instead (see
  `references/fail2ban.md` and `references/cloudflare.md`).
- **Whitelisting is safer than disabling.** The 7G design lets you disable and
  re-add an edited rule; prefer that over switching off a ruleset.
- **Suspected compromise:** do not "clean up" before preserving logs; rotation or
  deletion destroys evidence.
